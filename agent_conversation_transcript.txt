1.  PROJECT SUMMARY The project is a Python-based, rule-driven
    deletion-audit agent. It examines deletion requests and available
    evidence, then produces a structured CSV report describing whether
    deletion is complete, incomplete, or not applicable.

Main technologies and concepts: - Python - CSV and JSON processing -
Timestamp and audit-cutoff filtering - Structured evidence inspection,
including JSON and SQL-related evidence - Deterministic step ordering
and output validation - VS Code and PowerShell on Windows

Expected output: - File: output.csv - Exactly 518 rows, one per deletion
request - Sorted by case_id - Columns:
case_id,deletion_status,steps_json - Status values: COMPLETE,
INCOMPLETE, NOT_APPLICABLE - Step objects contain: step_no, phase,
system_id, resource_id, operation, state, evidence_id - Phases: FINDING,
REMEDIATION, VERIFICATION

5.  LIKELY AI JUDGE QUESTIONS AND ANSWERS

Q1. What is your project about? A. It checks whether a customer’s data
has been properly deleted after a deletion request by examining evidence
and producing a structured report.

Q2. What problem does it solve? A. Deleting a main account may not
remove data from every connected system. The agent helps identify
remaining records and risks.

Q3. Which programming language did you use? A. Python.

Q4. What are the inputs and outputs? A. The inputs are the supplied
deletion-request dataset, identity information, rules, and evidence. The
main output is output.csv.

Q5. What do the three statuses mean? A. COMPLETE means evidence supports
completion; INCOMPLETE means work or evidence is still unresolved;
NOT_APPLICABLE means the person did not request deletion.

Q6. How does the agent work? A. It reads input files, matches identities
and resources, inspects evidence, applies rules, assigns a status, and
writes the required CSV.

Q7. Why is identity matching important? A. A person may have different
identifiers in different systems. Matching helps find the relevant
records without overlooking data.

Q8. Why check timestamps? A. Evidence after a request’s audit cutoff
must not be used to justify that request’s status.

Q9. What are FINDING, REMEDIATION, and VERIFICATION? A. FINDING
identifies relevant records and evidence; REMEDIATION lists the required
corrective actions; VERIFICATION checks whether the required outcome is
supported.

Q10. What is the difference between evidence and a proposed action? A.
Evidence describes what is observed. A proposed action describes work
that should happen; it is not proof that the work has already succeeded.

Q11. How is structured evidence handled? A. The code uses
file-processing logic to inspect structured evidence such as JSON and
SQL-related records, depending on the format.

Q12. Why does output formatting matter? A. The evaluator expects the
exact row count, column names, valid JSON step objects, and required
ordering.

Q13. How are active data flows handled? A. An active flow may continue
moving customer data. The agent should identify it and include
appropriate remediation and verification steps.

Q14. How was the project tested? A. The provided evaluation scripts and
three custom regression cases were run. The custom tests passed, but the
overall sample evaluation failed.

Q15. What would you improve? A. I would improve identity matching,
evidence extraction, remediation planning, verification logic, and OCR
support for screenshot evidence.

Q16. What was the biggest challenge? A. Interpreting evidence correctly
and generating the exact expected status and ordered steps for each
request.

Q17. Is this a trained AI model? A. The current implementation is
primarily a Python rule-based agent. I should not claim it uses a
trained machine-learning model or an LLM API unless that is actually
implemented.

Q18. What did you learn? A. I learned to process datasets, inspect
evidence, apply rules, validate output formats, and test against strict
requirements.
